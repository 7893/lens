# ADR-0005: Lens 2.0 次世代架构演进与重构蓝图

更新日期：2026-09-19
状态：提议
责任人：@lens-team
适用范围：全系统架构演进（检索内核、边缘拓扑、数据一致性、图源生态、前端交互）

---

## 背景 (Context)

Lens 1.0 的现行架构成功验证了“基于 Cloudflare 边缘计算栈（Workers + D1 + Vectorize + Workers AI + R2）构建零冷启动混合图像检索”的工程可行性，并在低延迟响应与自动化门禁上取得了良好成效。

然而，随着系统持续演进，现行技术方案在深入落地时暴露出以下 **5 大核心架构瓶颈**：

1. **拟多模态与视觉信息衰减**：目前检索本质上是“文本中介模式”（图片 -> Llama 4 Scout 生成英文 Caption -> BGE-M3 向量化）。图片的构图、细微色调、艺术流派等视觉细节在文字转译过程中损失严重，且系统完全无法支持现代用户刚需的“以图搜图”或“复合调制检索”；
2. **单 Worker 巨石拓扑争抢资源**：当前 `@lens/engine` 单 Worker 囊括了静态资源托管、高并发低延时的搜索网关、重内存消耗的视觉理解、长耗时的 Workflow 状态机和定时调度（Cron）。高并发搜索（要求 128MB 极简内存、微秒级冷启动）与重型流水线绑定在同一执行实例中，故障域未隔离；
3. **异构存储缺乏事务保障导致的裂脑**：关系表与全文索引（D1）、密集向量库（Vectorize）以及 WebP 图片切片（R2）分属不同的存储产品。当后台流水线部分步骤超时重试时，缺乏分布式事务机制，容易产生 `vectorize_synced = 0` 的悬挂脏数据；
4. **摄取流水线对单一第三方 API 强耦合**：`IngestionService` 与数据契约深度绑定了 Unsplash API。当触发 Unsplash 50 次/小时频控限制时，新图摄取全线停转，系统缺乏多图源适配与故障自愈转移能力（对应未决问题 `KI-001`）；
5. **领域状态流转分散与前端交互维度单一**：摄取生命周期状态缺少聚合根统摄；前端仅支持简单的关键字输入框，缺乏以图搜图拖拽抽样、冷暖色系直方图筛选与链路性能感知。

---

## 决策 (Decision)

我们提议启动 **Lens 2.0 次世代架构演进计划**，确立以下 **5 大重构工程支柱**：

```text
+---------------------------------------------------------------------------------------+
|                                    LENS 2.0 ARCHITECTURE                               |
+---------------------------------------------------------------------------------------+
|  [前端] React 19 + 拖拽以图搜图 + 颜色直方图筛选 + SSE 流式渐进渲染 + 链路追踪大盘      |
+---------------------------------------------------------------------------------------+
|  [边缘接入层] Lens Gateway Worker (128MB / 低延时网关 / L1 HTTP 缓存 / FTS5+向量秒级召回) |
+-------------------------------------------+-------------------------------------------+
                                            | Workers RPC (零网络损耗内部函数调用)
+-------------------------------------------v-------------------------------------------+
|  [流水线与推理层] Lens Processor & Agent Worker (高内存 / Workflows / 视觉理解 / 配额审计) |
+---------------------------------------------------------------------------------------+
|  [检索内核] 原生多模态双塔空间 (Vision Tower + Text Tower) -> 文搜图 / 图搜图 / 复合检索  |
|  [数据治理] D1 事务发件箱 (Outbox Pattern) -> 可靠队列驱动 Vectorize / FTS5 / R2 同步   |
|  [图源生态] 可插拔适配器 (Pluggable Adapters) -> Unsplash / Pexels / R2 直传 / S3 同步 |
+---------------------------------------------------------------------------------------+
```

### 1. 检索内核：建立原生多模态联合表征空间

- **视觉特征直连**：引入原生图文联合嵌入模型（如 SigLIP / 现代视觉编码器）。在摄取阶段，直接提取图片张量的密集嵌入向量落入 `VECTORIZE`，原汁原味保留构图、色系和画风；
- **全模态检索能力**：
  - **文搜图（Text-to-Image）**：文本通过同一潜在空间 Text Tower 投影，直接检索图片真实像素特征；
  - **以图搜图（Image-to-Image）**：用户上传或拖入图片，提取特征向量后秒级召回视觉相似与画幅相似的图片；
  - **复合调制检索（Composed Search）**：支持“图 + 文”混合指令（如：“这张图片的构图，但换成赛博朋克霓虹色调”），通过向量空间代数调制检索；
- **两阶段渐进式投递（Progressive SSE Stream）**：首屏秒级推送低带宽 `blurhash`，背景异步并发完成重排与元数据水合。

### 2. 边缘拓扑：基于 Workers RPC 实施微核解耦

- **分层拓扑**：利用 Cloudflare 提供的 **Workers RPC**（同账号跨 Worker 内存级直通调用，无 HTTP 序列化开销与跨域成本），将单 Worker 拆解为双核：
  1. **Lens Gateway Worker**：极轻量（128MB 限制），专注处理在线搜索请求、边缘 HTTP/KV 缓存与 FTS5/Vectorize 双路秒级召回；
  2. **Lens Processor & Agent Worker**：专注长耗时的视觉特征编码、Queue 削峰消费、Workflow 摄取流转与 AI Gateway 配额审计；
- **故障隔离**：后台批处理或大模型超时崩溃绝不波及前台在线搜索。

### 3. 数据一致性：基于发件箱模式（Outbox Pattern）彻底消灭裂脑

- **D1 本地事务保障**：任何图片元数据入库时，在 D1 主事务中同时写入 `images` 表与 `outbox_events` 表；
- **可靠队列最终一致性**：由独立的消费器从 `outbox_events` 读取事件，幂等重试推进 Vectorize 向量构建、FTS5 全文索引更新与 R2 WebP 生成；全量成功后标记事件完成。即使网络抖动或平台限流，系统也能自愈重试，保证多维存储的最终一致性。

### 4. 摄取生态：抽象通用可插拔适配器（Adapter 模式）

- **解耦服务商依赖**：定义通用的 `ImageProviderAdapter` 接口契约：
  ```typescript
  export interface ImageProviderAdapter {
    readonly providerName: string;
    fetchLatest(page: number, limit: number): Promise<StandardImagePayload[]>;
    getRemainingQuota(): Promise<number>;
  }
  ```
- **多源并发接入**：
  - **公共图源**：Unsplash 适配器、Pexels 适配器（当主图源被 429 频控时，自动平滑 Failover 到备选图源）；
  - **自主图源**：支持通过 Presigned URL 用户直传至 R2，经由 R2 事件驱动自动化摄取；
  - **外部存储同步**：支持 S3 桶或外部图床批量挂载建立索引。

### 5. 领域充血与前端交互演化

- **领域聚合根**：引入 `IngestionLifecycleAggregate`，将图片生命周期状态（Pending -> Processed -> Vectorized -> Evolved）收敛于聚合根内部，对外暴露原子业务操作；
- **前端交互革新**：
  - 支持将外部图片拖拽入搜索栏触发以图搜图；
  - 增加色系直方图（冷色调、暖色调、黑白灰）与纵横画幅比（全景、竖屏壁纸、正方形）维度筛选；
  - 集成基于 [ADR-0001](0001-custom-agent-tracing.md) 的端到端链路耗时瀑布图面板，为高阶用户呈现微秒级可观测性。

## 理由与考量 (Rationale)

| 决策点          | 采纳方案             | 评估过的替代方案                 | 权衡考量与妥协                                                                                                   |
| :-------------- | :------------------- | :------------------------------- | :--------------------------------------------------------------------------------------------------------------- |
| **检索表征**    | 原生多模态联合表征   | 现有“Llama 4 生成文本后再向量化” | 原生多模态彻底解决了视觉信息失真，支持以图搜图；妥协是需要重构入库时的特征提取流水线。                           |
| **Worker 架构** | Workers RPC 双核解耦 | 继续维持 Single-Worker 巨石      | 双核拓扑彻底隔离了故障域并匹配了各自最佳内存规格；利用 Cloudflare Workers RPC 避免了传统微服务引入的 HTTP 延迟。 |
| **数据一致性**  | D1 事务发件箱模式    | 两阶段提交 (2PC) / 定期扫库修数  | 边缘计算环境无 2PC 支持，发件箱模式利用现有 D1 + Queue 即可实现坚固的最终一致性，免除人工修数。                  |
| **图源扩展**    | 适配器模式 (Adapter) | 继续单一写死 Unsplash            | 消除对单一第三方 API 的依赖脆弱性，解决 `KI-001` 历史顽疾。                                                      |

## 影响与实施路径 (Consequences & Roadmap)

### 正面收益

- **搜索能力飞跃**：从单向文字搜图跨入文搜图、以图搜图与复合调制的真正多模态时代；
- **系统高可用与稳定性**：在线搜索网关不再受后台大模型与爬虫崩溃的影响，可用性达到生产级四条九（99.99%）；
- **数据一致性闭环**：彻底解决存储分片之间的状态不同步问题；
- **生态扩张能力**：支持用户自主上传与多图库接入，打破数据源壁垒。

### 分阶段演进路径 (Milestones)

1. **Phase 1（图源解耦与熔断自愈）**：抽象 `ImageProviderAdapter`，重构 `IngestionService`，解决活跃问题 `KI-001`；
2. **Phase 2（数据发件箱与一致性加固）**：在 D1 引入 `outbox_events`，重构 Queue 消费者，保障存储同步幂等性；
3. **Phase 3（边缘拓扑解耦）**：通过 Workers RPC 将网关与流水线解耦为双 Worker；
4. **Phase 4（真·多模态与前端革新）**：升级视觉编码器，实现以图搜图与前端流式交互。
